# ADR-0015: A simple, conventional backend

Status: Accepted
Date: 2026-09-29

Supersedes ADR-0001 (module packages), ADR-0002 (Drizzle, schema per module), ADR-0003 (Keycloak), ADR-0004 (Turborepo, Vitest, zod, pino), ADR-0006 (outbox, for now), ADR-0009 (five database roles), ADR-0010 (contract-first OpenAPI files), ADR-0011 (service packages) and ADR-0014 (local Keycloak). ADR-0005 (ids, time, audit), ADR-0012 (local PostgreSQL, no Docker) and ADR-0013 (separate frontend and backend repositories) still apply.

## Context

The first implementation split the backend into about ten packages with facades, injection tokens, an event outbox, a worker, a device gateway, a separate login server and a custom contract build. The project owner found it too complex: the request flow was hard to follow, `node_modules` appeared in many folders, and interns and freshers could not understand or change it. The product needs clear, conventional code more than it needs preparations for scaling it doesn't have yet.

## Decision

- **One NestJS app, one package** (`src/`), organised like the NestJS documentation: `src/modules/<feature>/` with a controller, a service, DTOs and a module; shared guards, decorators, middleware and filters in `src/common/`.
- **Prisma** for the database: one schema file (`prisma/schema.prisma`), Prisma migrations, one PostgreSQL schema (`public`), snake_case tables.
- **Organizations (tenants) are kept apart twice:** every query filters by `organizationId`, and PostgreSQL row security (policies in the migration) hides other organizations' rows. Services use `prisma.forOrganization(id, …)` or `prisma.forAllOrganizations(…)` (super admin and login only). Two database roles: `edu_owner` (migrations) and `edu_app` (the app).
- **Login in the backend:** email + password (bcryptjs), a signed JWT (`@nestjs/jwt`, `passport-jwt`). Two login routes: super admins and organization users. Every request reloads the user, so deactivation and suspension work immediately.
- **Access rules as decorators:** `@Public`, `@LoggedIn`, `@SuperAdminOnly`, `@OrganizationUser`, `@RequirePermission('module.resource.action')`. A global guard refuses any endpoint without one.
- **Validation** with class-validator DTOs; **API documentation** generated by `@nestjs/swagger` from the controllers and DTOs (`/api/docs`, `/api/docs-json` for Postman).
- **Tests** with Jest: unit tests next to the code, end-to-end tests over HTTP against a temporary database.
- **Not now:** event outbox, background worker, biometric device gateway, Redis, multi-factor login, password reset by email. Each is added when the feature that needs it is built.

## Consequences

- A fresher can follow a request from the controller to the database in a few files, and the structure matches the tutorials they already know.
- Moving one feature into a separate service later is more work than with the old packages; accepted, because it may never be needed.
- The detailed design documents (doc 7 database design, doc 8 API conventions, docs/modules) describe the intended product; where they mention the old structure (schemas per module, outbox, Keycloak), this ADR wins.
